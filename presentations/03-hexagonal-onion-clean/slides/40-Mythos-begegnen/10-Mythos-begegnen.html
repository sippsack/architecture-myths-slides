Cockburn, 2005

Hexagonal Architecture
(Ports & Adapter)

  • Kennt nur "innen" (Application) und "aussen" (alles andere)
  • Application von Technik entkoppelt
  • "Dependency Rule"
  • Dependency Inversion
  • Strikte Verantwortlichkeiten der Bausteine:
    • Ports: fachlich motivierte Interfaces
    • Adapter: technische Anbindung an Umwelt
    • External Actor Systeme, Prozesse, Rollen, Benutzer, ...
    • Anbindung: Driven / Driving

Palermo, 2008

The Onion Architecture

  • Teilt wichtigste Charakteristiken von hexagonaler Architektur
  • macht zusätzlich Aussagen über “das Innere”
  • Kritikpunkte:
    • “Layeritis”: “too much” für kleine Projekte
    • DDD: Domain Services getrennt vom Model?

Offensichtlich eine Variante der Relaxed Layer Architecture

Nachteile:

  • Erfordert disziplinierte, strikte Umsetzung
  • Codebasis kann für kleinere Vorhaben zu komplex strukturiert sein
  • Trennung von Domain Services und Domain Model: Wirklich praktikabel?
  • Wie würden wir das paketieren?
  • Meinung: Obwohl auf den ersten Blick offenbar DDD eine zentrale Motivation darstellt, verleitet Onion zu unsauberer Strukturierung der Domain-Logik

→ Subtile Unterschiede zwischen Hexagonal und Onion schon erkennbar

Gemeinsamkeiten Onion & Hexagonal

  • Strikte Trennung von Applikation und Infrastruktur-Code
  • Entkopplung über dedizierte Adapter

Onion-spezifisch

  • Macht Aussage über "das Innere" der Applikation
  • Erlaubt auch noch mehr Schichten innerhalb der Applikation
  • Entspricht einer Relaxed-Layer-Architecture mit strikter Anwendung des Dependency Inversion Prinzips
  • Ports (Interfaces) sind implizit

Martin, 2012

Clean Architecture

Konsolidierung ähnlicher Ansätze:
  • BCE (Jacobsen, 1992)
  • Ports & Adapters (Cockburn, 2000)
  • Onion Architecture (Palermo, 2008)
  • DCI (Coplien, Reenskaug, 2010)
Explizite Hinweise zur Umsetzung, z.B:
  • Anzahl der Schichten nicht fest vorgegeben(!)
  • Nur simple Datenstrukturen sollten Schichtengrenzen überschreiten
  • Austauschbarkeit von Schichten / Segmenten, wenn diese obsolete werden → Evolution

Konsolidierung ähnlicher Ansätze:

  • Onion Architecture (Jeffrey Palermo, 2008) – Feinere Aufteilung in Form von Ringen
  • Clean Architecture (Robert C. Martin, 2012) – Fokus auf Modularität anstatt Adaptionsfähigkeit

Dependency Rule

Abhängigkeiten sind nur zu weiter innen liegenden Ringen gestattet.

Ziele dieses Ansatzes:

  • Trennung von fachlicher und technischer Implementierung (Modularität)
  • Flexibilität bzgl. Technologien, Infrastruktur und Umsystemen (Adaptionsfähigkeit)

Typische Ringe:

  • Core → Domain: Modell der Domäne
  • Core → Domain Services: Algorithmen und Prozesse der Domäne
  • Application: Orchestrierung von Fachlichkeit und Informationen von Außen
  • Infrastructure: Ring bestehend aus vielen Teilstücken
    • Technologien und Frameworks
    • Adapter zu Umsystemen
    • Schnittstellen
    • Tests (Outside-In-Testing)

Quellen:

Tipps für Pragmatiker

  • kleine Systeme: Hexagonal mit einfacher innerer Struktur reicht vielleicht aus
  • Benefit von Abstraktion durch weitere Schichten?
  • Ist “Schichten austauschen können” ein relevantes Qualitätsziel?
